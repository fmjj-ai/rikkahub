## 一、结论与范围

两项需求都可以在现有架构内实现，不需要修改可视化协议、不需要引入系统悬浮窗权限，也不需要重写已经正常的画布缩放。

采用用户优先选择的方案一：**全屏画布与可折叠、可拖动、可调整尺寸的悬浮控制窗分层显示。** 不采用把画布和全部按钮作为一个大页面一起拖动的方案二。画布已有的平移和缩放继续保留，但它们只作用于画布，不带着按钮一起移动。

聊天问题必须同时处理两件事：

1. 消除生成结束前后 Markdown 正文短暂消失、消息高度塌缩的原因。
2. 取消生成结束和后续布局变化引发的自动拉底，保留生成过程中的正常跟随以及用户主动浏览意图。

**不采用“先跳走、再拉回”的滚动补偿，也不增加生成结束后恢复旧锚点的自动跳转。** 列表位置应主要依靠稳定的消息身份、连续的正文快照和正常布局保持，而不是结束时追加定位命令。

本次需求边界：

- 删除卡片上的“点击查看全屏交互”提示句，保留标题点击及原有“放大”入口。
- 全屏中查看画布与点击“下一步”等操作不再需要来回上下滑动整个页面。
- 控制窗默认较小，可收起、展开、移动及调整宽高。
- 用户在生成中上滑阅读后，流式输出及生成结束都不能把用户拉走。
- 用户未上滑时，保留当前生成过程中的正常流式跟随。
- 生成结束后没有新的自动回底命令；用户主动点击回底、跳转消息、发送消息等显式操作仍保留各自语义。
- 后续实施完成后的交付目标是可安装的已签名 GitHub 分发 Release APK，而不是只完成 Debug 构建。

## 三、录屏与源码定位

### 3.1 录屏证明了什么

对约 6.425 秒的录屏逐帧检查，时间采用视频帧时间戳，不用平均帧率推算：

- **4.0370 秒**：最新回答正文正常显示，仍有生成指示。
- **4.0693 秒、4.0715 秒**：最新回答和上一条带 Kruskal 图卡的回答正文都暂时消失；头像、操作栏或用量信息仍存在。
- **4.0872 秒**：上一条回答的文字和图卡恢复，画面位于旧回答附近。
- **4.1241 秒**：两条正文已恢复，画面经过旧回答底部与最新回答开头。
- **4.1298 秒**：画面重新回到最新回答下方。

这不是单纯的滚动动画方向错误，也不是整个会话数据消失：**消息外层仍在，而正文内容经历了空白、恢复，再重新定位的过程。** 最新回答是普通文本，不含展开中的思考卡片，因此不能把此次现象主要归因于思考内容自动折叠。

本轮未收到独立的“图一”“图二”图片；关于全屏画布与按钮上下分离的定位，依据用户描述和实际全屏布局源码。提供的录屏用于核对聊天结束闪回。

### 3.2 正文空窗的直接代码条件

以下位置均以本次提交基线为准。

`app/src/main/java/me/rerere/rikkahub/ui/components/message/ChatMessage.kt:446–455`：

- 生成中直接调用 `textContent()`。
- 生成结束后改为 `SelectionContainer { textContent() }`。
- 这会改变正文子树的组合调用位置和父层结构。
- 此分支有既有原因：流式期间持续注册、注销可选择文本曾引发 `ConcurrentModificationException`，因此不能简单恢复为流式期间也启用文字选择。

`app/src/main/java/me/rerere/rikkahub/ui/components/message/AssistantMessageMarkdown.kt:33–60`：

- 助手文本默认进入支持可视化的 Markdown 准备分支。
- `prepared` 是组件内部的 `remember(conversationId, messageId, partIndex)` 状态，初值为 `null`。
- 解析经后台协程完成；普通文本也会进入这条准备路径。
- 输出使用 `prepared?.let { PreparedMarkdownContent(...) }`；准备状态为空时不渲染任何正文。
- `remember` 的 key 稳定，不等于状态能跨不同组合分支或 LazyColumn 项回收持续存在。

对照 `ui/components/richtext/Markdown.kt:161–218`：旧 `MarkdownBlock` 会保留已有快照，首次准备尚未完成时仍通过 `PreparedMarkdownContent` 显示文本。新增助手渲染路径缺少对应的首次展示保护。

因此，最新回答存在明确的问题链：**完成态选择包装切换 → 内部准备状态可能重新初始化 → 异步准备期间正文为空 → 列表内容高度骤减。** 录屏观察到的正文消失与这条链吻合。

上一条旧回答同时变空，最符合当前代码的解释是：最新回答高度塌缩改变可见区域，旧消息重新进入 LazyColumn 组合，其局部准备状态也从空开始。随后两条消息各自完成解析，正文先后恢复。这里的“旧项具体在哪一帧被回收”尚没有运行时生命周期记录，因此作为有证据支持的机制判断，而不是已经逐项记录的运行时事实。

### 3.3 第二次拉底是明确存在的主动行为

`ui/pages/chat/ChatList.kt:277–305`：

- `loading` 变化会调用 `scrollController.onGeneration(loading)`。
- 列表结构、可见项尺寸及 `canScrollForward` 变化也会通知控制器。

`ui/pages/chat/ChatScrollController.kt:115、159–185`：

- `onGeneration(generating)` 当前忽略参数，不区分开始和结束，直接调用 `onLayoutChanged()`。
- `intent.following` 为真时，只要布局出现可继续向下滚动的空间，就通过 `scrollToItem` 定位尾部哨兵。
- 代码注释明确要求“完成生成后仍按原意图处理最终重排”。

因此只删 `onGeneration(false)` 内的一次调用不够：正文重新出现、loading 项移除、消息操作栏出现等布局变化仍会触发同一自动拉底分支。必须在控制器的自动跟随资格和异步任务执行前共同限制。

### 3.4 没有发现的“原因”不应作为修改依据

- `ChatList.kt:335–359` 使用稳定的 `MessageNode.id` 作为 LazyColumn key。
- 当前消息身份为消息 ID 加分支索引，普通流式追加保留消息 ID。
- `ChatPage.kt:184–190` 按会话 ID 保存列表状态，不按 `loading` 创建新列表。
- `ChatList` 的 `AnimatedContent` 跟随 `previewMode`，不是生成状态。
- 没有证据说明生成结束会整体替换会话 ID、把所有消息 key 重建，或显式执行“回到上一条回答开头”。

所以不更换整套列表 key、不重建列表状态，也不改消息树结构来处理这次问题。

### 3.5 主代理复核后的因果结论

这次修复的主要对象是**正文准备状态的生命周期错误**，不是先猜一个滚动锚点再修补位置：选择包装切换没有保住其内部的准备状态，而准备尚未完成时组件确实会输出空正文。`key(block.index)` 位于包装之外，不能让包装内部两个不同组合位置自动共享普通 `remember`。旧 `MarkdownBlock` 有首次文本展示，新 `AssistantMessageMarkdown` 没有，这也是已提交差异中明确新增的退化。

同时，`onGeneration` 没有实际记录生成状态，`onLayoutChanged` 的自动定位资格不包含“正在生成”，这使任何完成后的尺寸恢复都可能变成第二次拉底。两个问题需要分别修正，不能用取消拉底代替正文连续展示，也不能用正文缓存代替用户阅读意图控制。

录屏确认了正文空白及恢复；源码确认了可导致它的状态重建与空输出路径。旧项在那几帧具体的回收/重建顺序仍未观测，不把它夸大为已取得运行时追踪的唯一解释。

## 四、全屏悬浮控制窗方案

### 4.1 当前上下分离的根因

`ui/components/visualization/VisualizationViewerHost.kt:270–306` 在一个 `verticalScroll` 区域中渲染完整 `VizRenderer`，同时按可用高度为画布分配接近整屏的高度。

`VisualizationBlock.kt:314–427` 把所有 `frame.nodes` 按顺序放入同一条竖向内容流，并递归渲染 `row`、`column`、`scene` 及控件。画布自己的缩放按钮又位于 `VizCanvas` 的下方。

因此图占据首屏以后，步骤按钮、参数及说明自然落到屏幕下方。问题不在于按钮事件失效，而在于**画布和操作控件共用整页纵向滚动布局**。

### 4.2 全屏结构

保留现有全屏 `Dialog`，不改成 Android 系统悬浮窗。全屏内采用如下层级：

1. 固定的顶部栏：标题、更多、关闭。
2. 占满剩余可用区域的主画布舞台。
3. 叠加在舞台之上的浮动控制面板。
4. 画布边缘的紧凑缩小、放大、复位工具条。

主舞台不再套住完整 renderer 的 `verticalScroll`。控制面板可以在自身内部滚动；滚动面板不会把主画布推到屏幕上方。

浮窗的移动、折叠和改尺寸不改变主画布分配到的宽高，也不触发画布重新适配。只有实际窗口、方向或可用主区域发生变化时，才沿用已有 viewport resize 逻辑。

### 4.3 默认尺寸与操作规则

以扣除系统栏、顶部栏、键盘及边缘留白后的可用舞台宽高 `W`、`H` 为基准，位置和尺寸统一保存为 dp 或归一化可用区比例，手势运算统一在 px 坐标系内完成转换。

初次打开一个图卡时：

- 面板默认展开，停靠舞台右下方，距离可用边缘 12dp。
- 默认宽度取 `min(280dp, 0.72 × W)`，默认高度取 `min(220dp, 0.32 × H)`，再按当前可用范围夹取。
- 正常最小展开尺寸为 200dp × 144dp；如果窗口不足以容纳这个最小值，以可用宽高为上限降级，不能让最小值反过来把面板撑出屏幕。
- 最大宽度为 `min(560dp, W)`，最大高度为 `H`；用户可主动放大，默认不占满画布。
- 折叠为约 144dp × 48dp 的短标题条，保留拖动区域、控件名称和展开按钮。
- 展开恢复上一次展开尺寸，不因反复收起而重新套用默认尺寸。
- 面板右下角提供可见的尺寸调整把手，触控命中区至少 48dp；标题栏拖动区与按钮命中区分开。
- 更多菜单提供“恢复控制窗位置与尺寸”，避免面板被用户放到不方便的位置后难以恢复。

控制窗不是全屏遮罩。点击它以外的画布仍可平移、缩放；面板内部按钮、滑块、输入框、正文滚动消费自己的手势，不能同时驱动画布。

键盘弹出时只计算临时可见位置和尺寸，保证标题栏和正在编辑的输入可访问；键盘收起后恢复用户偏好的展开尺寸，不把临时压缩结果永久写回。横竖屏变化按新的可用区域重新夹取，不能沿用失效的绝对像素位置。

窗口实在过小时，优先保留紧凑标题条和可展开入口，不强行给画布或面板设置超出可用区的固定最小高度。

### 4.4 按钮必须优先可达

不能只是把原来的长列原封不动塞进一个小浮窗，否则“下一步”仍可能藏在很长的说明之后。

控制窗内部提供按内容存在与否显示的分组：

- **操作**：步骤控制、播放/暂停、重置、本地动作按钮、发送给 AI 等操作。
- **参数**：滑块、数字输入、下拉选择、开关。
- **信息**：当前状态、步骤说明、序列、表格及其他文字。

默认打开有操作控件的“操作”组；没有操作时打开第一个非空组。空组不显示标签。有多排操作时保留面板内部滚动，不让固定标题栏随之消失。

有 v3 `controls`、`parameters`、`status` slot 时优先尊重声明；无 slot 的旧内容按节点类型确定组别。slot 为 `main` 的非画布信息进入信息组。不同组的展示顺序可以调整，但同组内控件保持原始相对顺序。

不根据“下一步”等按钮文案猜测语义，不重新生成动作，不复制同一可交互控件到多个位置。一个按钮在任一时刻只有一个可操作实例，原来的 `session.enqueueDispatch`、`enqueueInput`、`session.message` 仍是唯一执行入口。

### 4.5 在 UI 层拆分，不修改已有协议

现有协议允许 scene 嵌在 `row` 或 `column` 中，也允许多个 scene。v3 可有独立顶层 scene，编译后 ID 为 `__scene`；v1 fixture 中 scene 则位于 `view` 列表内。`plot` 是 scene 内部图元，不是独立控件。

因此不能只过滤顶层节点，也不能只取第一个 `scene` 后丢掉其余内容。

新增全屏展示投影，输入仍是同一份已编译 `VizFrame`：

1. 按原节点顺序递归遍历。
2. 遇到 scene，加入主舞台场景集合；scene 内部所有 shapes 保持原样，不能把 shape 类型的 text、plot 等误当面板控件抽出。
3. 非 scene 叶节点进入相应控制分组。
4. 对 `row`、`column` 递归保留属于该分组的子节点，移除空容器；非空容器继续保留原类型、values、error 及 ID。
5. 继续使用编译器已有节点 ID，不按投影后的新下标重建 identity。
6. 保留原节点动作和数据绑定，只改变全屏中的呈现位置。

**多 scene 的确定处理方式：**舞台增加紧凑的场景切换入口，按原顺序列出所有场景，初次选中第一个，显示“画布 1”“画布 2”等。当前 scene schema 没有独立名称字段，不能假设它已有 title/label，也不为此扩充协议。每个场景的 viewport 按原 ID 独立保存。切换场景不清空参数、步骤和其他场景状态。控制窗仍可访问整个可视化的全部控件，不假定每个控件只属于当前场景。

如果 `visible` 条件或流式更新移除了当前 scene，改选仍存在的相邻场景；暂时没有可见 scene 时显示控件内容，不持有失效节点。如果分组内容动态消失，也改选首个非空分组。动态显隐不重置仍存活场景的 viewport。

这种全屏模式不保留原来多个 scene 在 row 中并排的几何排布，但保留全部场景、原序和状态；普通聊天卡片继续按原结构渲染，不发生此变化。

没有 scene 的可视化，不制造空白画布或没有意义的覆盖层，使用完整的控件内容视图；有 scene、但没有额外控制节点时，不显示空控制窗，只保留画布工具条。

### 4.6 保留当前正常的画布交互

`VizViewport.kt` 中的缩放范围、中心、已调整标记、尺寸变化适配和边界夹取继续使用。当前缩放范围是 `0.5f..8f`，本次不更改。

需要调整的是 `VizCanvas` 的布局接口，而不是坐标变换算法：

- 将 Canvas 绘制区与其下方工具条分开，让全屏主区域直接提供实际可用尺寸。
- 全屏可隐藏 Canvas 原有的内联按钮，将按钮放入舞台角落的紧凑工具条；两处调用同一个 viewport 对象的方法。
- 不再依赖统一的 `maxHeight - 84.dp` 来同时给画布和整套内容预留空间。
- 保留双指缩放、已有平移边界及双击复位。
- 折叠控制窗、切换分组、点击下一步都不调用 viewport reset。
- `VizCanvas.kt:101–110` 当前会把平移到边界后剩余的手势交给外层页面滚动；新的全屏舞台不再存在那个整页滚动容器，需取消该模式下的剩余位移转交，不能把画布手势转发给浮窗或下面的聊天列表。其他仍需要嵌套滚动的调用路径保持原有语义。

新增可选参数放在尾部回调之前，保留现有尾随 lambda 调用兼容性。

### 4.7 状态和生命周期

在 `VizPresentationState` 中增加按 `sessionKey` 索引的控制窗状态，包含展开状态、用户偏好宽高、位置、当前分组及选中 scene ID。viewport 仍按 `sessionKey + scene identity` 保存。

采用明确的页面内保存范围：

- 同一聊天页面中关闭、重开同一图卡，恢复位置、尺寸、折叠状态和已选场景。
- 不同图卡分别保存，不能互相串用位置或输入草稿。
- 流式 `rikka-viz-stream` 使用已有稳定 session key，源码增量不重置控制窗。
- 普通非流式图卡源码摘要变化会产生新 session，按新图卡初始化；这与当前 session 语义一致。
- 来源消息、分支或 session 被清理时，同步清理面板状态；不按动态 frame 或 revision 创建一份新面板状态。
- 不把浮窗几何写入全局设置、数据库或 Android Bundle；页面销毁后可恢复默认，这一范围是本次完整实现的边界，不是待补功能。

继续复用现有 full-screen pin/unpin、来源失效关闭、数字草稿及 session 串行队列。主舞台与面板共用一个 session、同一份 frame，不额外挂载第二个完整 `VizRenderer`，不产生第二路流式解析或动作执行。

**数字输入需要一并改动，不能只口头声明草稿保留：**`VizWidgets.kt:129–135` 目前只根据“是否位于全屏”判断失焦是否属于 renderer 转移。收起面板、切换分组仍发生在全屏内，当前判断会把这类失焦视为普通失焦并提交。应在 presentation 中增加明确的展示转移原因或版本，在收起、换组、查看源码及退出之前先记录并保存草稿；输入框据此区分普通失焦与布局转移。转移只保存草稿，不提交；用户点击完成或正常转移到其他输入时维持原提交语义。不能靠固定延迟或长驻的全局“忽略失焦”标记处理。

## 五、Markdown 正文连续展示方案

### 5.1 准备状态与选择包装解耦

将现在 `AssistantMessageMarkdown` 同时承担的“准备”和“渲染”拆开：

- 准备所有者按会话、当前消息及分支身份、文本 part 索引稳定存在。
- 它位于 `loading` / `SelectionContainer` 条件包装之外，持有最后一个完整的 Markdown 快照和正在准备的输入。
- 渲染组件只消费已经存在的快照、可视化 renderer 和点击回调，不在选择包装内部重新创建准备状态。
- 生成中仍不启用文字选择；完成后只替换选择能力的包装，不清空准备结果。

允许内层 UI 由于选择包装变化重新组合，但新组合第一帧必须立即获得同一个已有快照，不能再从 `prepared=null` 开始等待。

不把 `source`、`loading`、frame revision 加进准备所有者的身份 key。普通流式文本更新只更新输入，不销毁状态所有者。

### 5.2 用有界页面缓存覆盖 LazyColumn 回收

仅把状态提升到某个消息内部还不够：整条 LazyColumn item 离开组合后，内部普通 `remember` 仍会丢失。

在 `ChatPage` 生命周期中增加独立的 Markdown 快照缓存，建议新增 `MessageMarkdownStateStore`，不把 Markdown AST 混进 `VizSessionStore`。缓存 key 至少包含：

- 会话 ID。
- 当前消息 ID 与分支身份。
- 文本 part 索引。
- 会影响显示的转换规则和渲染配置版本。

source 本身作为输入修订号与快照内容，不作为每个流式 chunk 都创建新条目的缓存 key。每个 key 只保存一份已提交快照及必要的在途准备状态。

输入修订还必须包含 `precedingSources` 或等价的前置围栏计数依赖：前面文本 part 的变化会影响后续图块的四块展示额度，即使当前 part 字符串不变，也可能需要重新准备。视觉正则及启用状态变化亦须使旧准备结果失效，不能只比较当前文本。

缓存初始边界采用最多 48 个非活动文本 part、约 2 Mi 字符加权预算，两者任一达到即淘汰最久未使用的非活动条目。权重统计原文、预处理文本、fence 文本等实际保留字符串，不能只计算回复字数。AST/DOM 有额外对象开销，因此字符预算不是堆内存精确上限；还需受现有解析资源限制及条目上限约束。

当前正在显示、生成或被全屏图卡使用的状态由活跃所有者持有，不因缓存淘汰而当帧归零；活跃集合超过缓存预算时不无限保留额外历史条目。条目失活后再按预算淘汰。

消息重新进入列表时先同步读取已有安全快照，再决定是否需要后台更新。会话切换、消息删除、分支身份失效、页面销毁时相应释放；不序列化 AST/DOM 到 Bundle 或数据库。

### 5.3 快照更新必须原子且有序

每个展示快照同时绑定 source、转换结果、AST/DOM、偏移信息和可视化 fence 映射，不能用旧 AST 搭配新字符串。

- 解析新 chunk 时保留上一份有效快照，完成后原子替换。
- 同一条消息的准备串行处理，输入可以合并到最新待处理版本，避免每个 token 启动独立解析任务。
- 后到达的旧任务不得覆盖已经提交的更新版本；会话、分支、配置身份变化后丢弃旧任务结果。
- 允许提交比当前展示更新的中间完整快照，再继续处理合并后的最新输入；不能要求每个结果必须等于不断变化的最新 source，导致高速流式过程中一直无法展示。
- 生成结束不清空缓存，不专门启动一次“先清空再解析最终内容”的流程。
- 可视化 fence ordinal、session owner 和已完成的 session 继续使用原有标识，不因文字选择启用而重新编号。

### 5.4 首次准备和失败时的展示

不能简单把缺失分支改成 `Text(source)`：包含 `rikka-viz` 的原始 source 带有 JSON/流式协议内容，直接展示会制造新的大段源码闪现和高度跳变。

完善准备状态，明确区分原始解析源、已准备快照和可直接展示的安全备用文本：

- 有旧快照：优先继续显示旧快照。
- 无旧快照的普通文本：显示与当前视觉转换规则一致的备用文本，随后切入准备结果。
- 含可视化候选围栏而尚无安全结果：显示简短、非零高度且不含源码的准备占位；后台识别围栏后，用围栏外的文字和图卡占位替代原始协议内容。
- 解析失败：保留最后有效快照，或显示已处理的备用文本与错误提示，不返回零高度正文。
- 只有用户主动进入“查看源码”时才展示原始图形协议。

既有“每条消息最多四个交互图块”的限制仍保留。超过额度的围栏应使用明确的额度提示和主动源码入口，不应在首次备用展示或失败路径中突然倾倒整段 JSON；普通非可视化代码围栏继续正常作为代码展示。

`VizFenceScanner` 对包含候选标记的内容会构建 Markdown AST，不是一个轻量字符串过滤器。因此不在主线程为备用展示额外调用完整 scanner，也不对每次重组重复解析。首次缓存未命中不承诺完全没有首次加载布局变化；承诺的是**已显示的正文不能因为生成结束或解析刷新而先被清空**。

## 六、滚动控制方案

### 6.1 将持续跟随与一次性跳转分开

控制器保留两种不同的权限来源：

1. 一次性显式请求：首次进入、用户点击回底、用户发送消息、路由指定消息等。
2. 持续流式跟随：正在生成，且用户仍允许跟随。

持续跟随条件明确为：

`正在生成 && 自动滚动已开启 && 用户仍处于跟随状态 && 未打开全屏查看器 && 当前没有用户滚动`

布局变化只是通知，不是授权。没有满足上述条件的情况下，消息尺寸、操作栏、标题、建议、loading 指示变化都不能新建回底请求。

### 6.2 生成结束的行为

当生成状态变为结束：

- 记录生成状态为非生成。
- 撤销这一轮已排队、尚未执行的自动流式跟随请求。
- 清除已经失去意义的本轮发送尾随请求，不能让它在最终布局恢复后迟到执行。
- 不创建 `scrollToItem`、`animateScrollToItem` 或 `scrollBy` 请求。
- 不恢复某个“上次生成前位置”。
- 不把 `following` 重新设置为 true。
- 不因为解析稍晚完成、loading 项移除或操作栏出现重新开放跟随。

用户刚刚点击的显式回底、路由定位等单独标注请求来源，不被误当成自动跟随一并取消。

如果最终解析结果在生成任务结束后才到达，仍更新正文，但不为追上最终末尾自动滚动。末尾新增少量内容可能需要用户主动向下查看，这是“结束时不额外跳转”的自然边界，不能再用一次强制拉底偷偷补回。

### 6.3 用户阅读意图优先

- 用户开始拖动、通过音量键翻页、跳转历史消息或执行其他明确浏览操作时，立即取消自动跟随及排队任务。
- 后续 chunk、生成结束、重新测量、图卡内容更新都不恢复自动跟随。
- 用户主动点击回底，可以在生成中恢复跟随；生成已结束则只执行一次回底。
- 用户确实主动向最新消息方向滚动并抵达真实尾部，也可恢复生成中的跟随。
- 不能只因布局变矮后 `canScrollForward=false` 就认为用户主动回到底部；用户滚动方向、操作来源和尾部哨兵可见必须共同支持这一判断。
- 新一轮显式发送沿用当前发送语义，不把上一轮浏览锁错误地永久应用到所有后续会话。

沿用 `DragInteraction` 区分用户拖动与程序滚动，完善取消事件及惯性结束处理。音量键、翻页、鼠标滚轮或可访问性滚动若能改变列表，也应进入同一意图入口，不能只照顾触屏。

### 6.4 防止异步竞争和“已经排队的一次拉底”

当前控制器会等待一个绘制帧后再定位。仅在入队前检查 `loading` 不够：等待期间用户可能已上滑，或者生成已结束。

加入请求来源和递增的操作版本号：

- 浏览开始、生成结束、切换会话、进入全屏都会使相关自动请求失效。
- 自动任务在等待帧之后、真正滚动之前，再检查生成状态、用户意图、版本号和查看器状态。
- 显式请求具有独立身份，不能被旧任务覆盖或反向恢复。
- 列表项 key、消息数及生成状态作为一次协调更新交给控制器，避免独立 `LaunchedEffect` 先发布新列表结构、后发布结束状态时，仍按上一帧的生成资格入队。
- 发送、重新生成、工具调用与可视化发送待处理状态共用明确的生成轮次，不能因为临时状态变化重复执行初始化回底。

保留当前稳定消息 key 和尾部哨兵，不在每次生成结束重建 `LazyListState`。

### 6.5 与其他布局变化的关系

正文空窗修好后，真实内容仍可能合法改变高度，例如思考折叠、最后操作栏出现、系统提示入口显隐、图片尺寸就绪。

这些变化不应重新授权滚动。对于本身会删除用户正在阅读区域的功能，需要遵守其独立交互规则；不能宣称在内容被删除或折叠后仍能保持同一个字符的绝对像素位置。

已有全屏查看器关闭时的来源锚点恢复属于用户主动关闭查看器的流程，不能复用于生成结束。关闭时也要受当前浏览意图和生成状态约束，不能在闲置态因 `following` 旧值而自动落底。

`ImeAutoScroller.kt` 是控制器之外的键盘避让入口。其现有显式输入体验保留，但要区分程序避让与用户浏览；不能让键盘引起的尺寸变化重新打开流式跟随，也不能用它承担结束时纠偏。

## 八、逻辑一致性、兼容与性能约束

完整实现应同时满足以下约束，而不是只让单个入口表现正确：

- 卡片与全屏共用 session，控制面板不会生成第二套业务状态。
- 浮窗隐藏不等于停止 session；恢复时步骤、参数、输入草稿保持一致。
- 源码、诊断、复制和发送给 AI 继续可访问；源码/诊断使用独立覆盖层或详情界面，不能挤压主画布。
- 发送给 AI 仍受当前助手授权和发送中状态约束，不能因控件搬家绕过禁用条件。
- 面板折叠时隐藏的输入控件不会因失焦被错误地自动提交；继续尊重已有草稿转移约定。
- 多 scene 不丢数据，旧 v1 与 v3 内容都可显示；普通卡片不改变原顺序。
- 全屏投影按 frame 更新计算，拖动只更新几何，不重新编译 spec、不重复解析 Markdown、不遍历协议字符串。
- 缓存有界，后台解析有序，失效结果不串到其他会话或分支。
- 生成结束不会触发新的自动定位，正常流式跟随不会因修复被整体禁用。
- 不改变全局设置、文件编码、用户自定义提示词或已有签名配置。

本次不承诺面板位置跨应用重启保存、不提供系统级跨应用浮窗，也不把任意可视化改成可整体二维拖动的网页。这些均不属于完成当前体验所必需的能力。
