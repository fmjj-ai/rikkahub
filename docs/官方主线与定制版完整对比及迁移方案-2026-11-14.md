> 核查日期：2026-11-14。本文依据两个目录的实际工作树、Git 状态、现有 APK，以及官方 GitHub Release APK 编写。
>

>
> 官方主线：`D:\PythonProject\ky\main\rikkahub`。
>
> 本次交付是分析和实施方案；没有迁移应用代码，没有构建、安装依赖或修改 Git 状态。文中“已确认”来自源码或产物检查；“建议”是后续设计；未做真机或运行时验证的项目单独注明。

## 1. 结论与建议范围

1. **官方约 16 MB 是真实的。** 官方 GitHub 发布的 `rikkahub-3.2.0-arm64-v8a.apk` 为 **16,325,647 字节，即 15.57 MiB**。当前已有 arm64 Release APK 为 **40,668,227 字节，即 38.78 MiB**。两者相差 **23.21 MiB**，当前约为官方的 **2.49 倍**。
2. **主要差距来自打包资源和原生库，而不是 Kotlin 业务代码数量。** 当前 APK 的 assets 比官方多 **12.09 MiB**，原生库多 **5.90 MiB**，两项合计解释总差额的 **77.51%**；DEX 只多 **0.28 MiB**。词典、横幅、英语素材、MuPDF 和 ML Kit 扫码相关内容是已经定位的大项。
3. **两边都已启用 Release 优化。** 当前使用旧式 minify/shrink 配置，官方使用新版 AGP optimization DSL。当前有 `-dontobfuscate`，但这不等于关闭代码裁剪。不能把 16 MB 与 39 MB 的差别简单解释为“官方开混淆、你没开”。
4. **以当前工作树为基底，按功能移植官方增量。** 当前有多协议提供商、OAuth 凭据保护、英语资源、函数绘图、相机转场、会话写入等定制。直接用官方目录覆盖，或为了缩包删除看起来大的目录，会损失这些能力。
5. **不迁入官方新版会话式 MediaCreation。** 当前仍保留旧 ImgGen 生图/编辑页和图集；新版 MediaCreation 入口已停用，但数据库还有残留结构。二者与聊天内 GPT Image 不是同一个功能，不能混为一谈。
6. **GPT Image 值得借鉴的是 Responses 的图片流处理。** 当前已有内建图像生成入口和最终图片处理，但缺少官方 Responses decoder 的 partial-image 事件与按图片 item ID 聚合。当前独立 Images API 反而已有自己的流式预览，不能整体替换成官方实现。
7. **Phone-use 按 GitHub 渠道完整迁移。** 需要渠道配置、无障碍服务、控制器、逐助手开关、工具注册、截图持久化、手势指示器与工具 UI。还应修正官方操作期间隐藏浮窗造成停止按钮短暂不可用的问题。
8. **本轮推荐顺序：保全当前工作树 → GPT Image 增量 → GitHub 渠道隔离 → Phone-use → 单独评估缩包。** 官方会话配置快照、Terminal/SSH、记忆整合等列为后续可选项目，不作为这两项功能的强制前置。

### 3.4 构建配置解释了什么

| 项目 | 当前 | 官方 | 结论 |
|---|---|---|---|
| ABI | arm64-v8a、x86_64，另产 universal | 相同 ABI 选择与拆分 | 本次用 arm64 对 arm64，已排除 universal 对比偏差 |
| Release 代码裁剪 | `isMinifyEnabled = true` | `optimization { enable = true }` | 双方有优化配置 |
| Release 资源优化 | `isShrinkResources = true` | 新版 optimization DSL | 不应因未出现旧属性名而判定官方未收缩资源 |
| ProGuard | optimize 默认规则；另有 `-dontobfuscate` | 官方自身规则，并发布 mapping | 当前禁名称混淆不等于禁删除无用代码 |
| R8 full mode | 未发现显式 `android.enableR8.fullMode=false` | 同样未发现 | 不支持“当前关了 full mode”结论 |
| 二维码识别 | Quickie bundled、ML Kit barcode | ZXing + CameraX | 能与实际扫码原生库/模型差异相互印证 |
| 文档实现 | 含 MuPDF Java/native | 不含对应 MuPDF native，PDF 实现不同 | 替换前要验证解析能力，而不是只删依赖 |
| 渠道 | 无官方式 distribution flavor | GitHub / Play | 渠道对比必须一致；本次官方是 GitHub 发布 APK |

源码位置：当前 `app/build.gradle.kts:32–46、74–88、242–248`，官方同文件 `34–48、76–104、116–129、282–286`；当前 `app/proguard-rules.pro:30`；双方 `gradle/libs.versions.toml`、`gradle/wrapper/gradle-wrapper.properties:4`。官方 CI `.github/workflows/daily-build.yml:93–113` 构建 `assembleGithubRelease`，收集 `apk/github/release/*.apk`。

AGP 优化语义参考：[启用应用优化](https://developer.android.com/topic/performance/app-optimization/enable-app-optimization)、[定制资源保留规则](https://developer.android.com/topic/performance/app-optimization/customize-which-resources-to-keep)。这些文档用于解释 DSL，不代替本报告的 APK 实测。

### 3.5 缩包建议：先处理资源，再评估功能替换

| 顺序 | 建议 | 需要保留或验证的能力 | 可量化边界 |
|---|---|---|---|
| 1 | 优化三张 banner 的分辨率/编码；按实际显示尺寸评估 WebP 等格式 | 检查所有引用方式、透明度、WebView/原生加载兼容及视觉效果 | 现有成本约 5.00 MiB；不是承诺可节省全部 |
| 2 | 评估词典和英语资源是否适合可选资源包、首次使用下载或精简版本 | 离线使用、首次启动、完整性校验、资源升级、搜索效果 | 表中词典与英语数据已有明确成本，但需先查使用链路 |
| 3 | 对照官方 ZXing 实现替换 bundled 扫码方案 | 相机预览、识别率、弱光/旋转、多种二维码、无网可用 | 扫码库+模型约 2.85 MiB；替代库也会占空间 |
| 4 | 对照官方 PDF 实现做能力评估，再决定是否替换 MuPDF | 中文/日文、字体、加密 PDF、大文档、分页、OCR 组合路径；图片型 PDF 的原有行为 | 单个 MuPDF native 当前约 4.36 MiB；净节省必须重建测量 |
| 5 | 审核 `res/`、资源表、其余 ZIP 条目和剩余 assets | 语言、主题、图标、Web 静态资源、反射引用 | 尚有明确差额未做逐文件归因 |
| 6 | 最后评估名称混淆规则和更细的 R8 keep 规则 | 序列化、JNI、反射、第三方 SDK、崩溃定位 | DEX 总差额仅约 0.28 MiB，不应优先押注这一项 |

不要直接删除词典：需先确认哪些数据是运行必需、哪些是可替换辅助数据。不要删除 MediaCreation 残留数据库结构来追求大幅缩包：目前没有证据表明它是主要成本，反而存在旧数据库兼容风险。

**目标应是“在保留指定功能的前提下减小体积”，而不是先承诺回到 16 MB。** 保留全部离线词典、英语素材和原有 PDF/扫码实现时，复制官方 Gradle 配置不足以达到官方大小。

## 4. 完整功能对比矩阵

“双方共有”只说明两边存在相同类别的能力，不代表代码、行为或所有边界情况完全一致。优先级：**必须保留**为当前迁移不变量；**本轮**为用户指定目标；**后续可选**不扩大本轮范围；**排除**表示不迁移。

| 功能范围 | 当前定制版 | 官方主线 | 建议 |
|---|---|---|---|
| AI 基础 provider | OpenAI、Google、Claude、ChatGPT 等 | 同类基础 provider，并有更多拆分实现 | 方法级比较，不整组覆盖 |
| 多协议提供商 | 有 `MultiProtocol`、协议端点解析及配置 | 未发现同等 `MultiProtocol` / `ProviderProtocol` 抽象 | **必须保留**，包括设置、模型、导入导出和测试 |
| ChatGPT OAuth | 有账号管理、刷新及凭据保护 | 同样有账号管理和 ChatGPT OAuth | 共有；保留当前刷新串行化与脱敏 |
| Grok 账号 | 当前未见官方同等流程 | 有 `GrokAuth`、`GrokProvider` 和账户配置 | 后续可选，不影响 GPT Image / Phone-use |
| Claude OAuth / CodeAssist | 本次未确认 | 本次检索也未找到对应 OAuth 实现 | 不把 Claude API 支持误报成 OAuth 新功能 |
| OpenAI 流式协议 | 主要在 provider/ResponseAPI 内解析 | 有独立 stream decoder、ID 化 chunk | **本轮择取图片部分**；全流模型重构另立项目 |
| Google 新接口 | 已有 Google 基础实现 | 有 Google Interactions API 等增量 | 后续按使用需求移植 |
| GPT Image 聊天内生成 | 已有 Responses 内建工具和最终图 | 有 Responses partial-image/ID 化聚合 | **本轮完善**，见第 7 节 |
| 独立图片生成/编辑 | 旧 ImgGen、图集、Images API；有独立流式预览 | 同样有旧图片功能，另有新版媒体流程 | 保留当前能力，避免全量覆盖 |
| 新版 MediaCreation | 入口停用，部分数据库结构仍保留 | 独立会话、任务、服务、历史与页面 | **排除新版流程迁移** |
| 助手上下文与压缩 | 有上下文限制、压缩、记忆 | 基础能力共有 | 不重复移植，保留当前边界行为 |
| 会话配置快照 | 无同等 `ConversationConfig` 快照 | 会话保存模型、推理、搜索、MCP、workspace、skills 等配置 | 后续高冲突项目；不是本轮前置 |
| 会话和消息持久化 | 有当前自己的 Session、节点写入方案与修改 | Session 管理和写入方式不同 | **必须保留数据一致性**，不可整文件替换 |

## 7. GPT Image 借鉴与迁移方案

### 7.1 当前与官方的真实差别

| 细节 | 当前实现 | 官方实现 | 建议 |
|---|---|---|---|
| Responses 工具声明 | `BuiltInTools.ImageGeneration` → `image_generation` | 同样有 | 沿用现有能力入口 |
| 源码中的模型字符串 | `gpt-image-2` | `gpt-image-2.5-sunburst` | 只是各工作树中的字符串；未验证服务端支持，不能机械更新 |
| Responses 解析位置 | `ResponseAPI.parseResponseDelta` → `MessageChunk` | `ResponseApiStreamDecoder` → `StreamChunk` | 借鉴设计，不直接套不兼容返回类型 |
| 图像开始/最终结果 | `output_item.added/done`，空 Image 后接最终结果 | item ID 对应 start/snapshot/end | 补可靠的逐图身份 |
| Responses 中间预览 | 未找到 partial-image 事件分支 | 处理 `response.image_generation_call.partial_image` | 本轮核心增量 |
| 图片合并 | 连续 Image 主要看最后一个 part | 按图片 item ID 管理 | 防止多图串接和预览重复累积 |
| 独立 `/images/generations` | 单图有 `stream + partial_images` | 所查对应实现无同等流式分支 | 保留当前优势，不能全量覆盖 |
| 独立 `/images/edits` | multipart，本地参考图片 | 同类接口，并有 OpenRouter 分支 | 只迁需要的差异与测试 |
| base64 落盘 | 聊天生成完成后 transformer 处理 | 整体消息流结构不同 | 沿用当前文件系统，补取消/错误路径 |

当前 `OpenAIProvider` 中的 `image_generation.partial_image` 等事件属于**独立 Images API**；官方 Responses 使用 `response.image_generation_call.partial_image`。事件名相近，不代表当前聊天 Responses 路径已经具备中间图片显示能力。

### 7.2 源码证据

以下路径中的 `ai/` 均相对各仓库根目录：

- 当前 `ai/src/main/java/me/rerere/ai/provider/providers/openai/ResponseAPI.kt:317–318`：内建工具声明；`:515–685`：当前 Responses 事件解析；`:561–603`：图片开始；`:635–685`：最终图像。
- 当前 `ai/src/main/java/me/rerere/ai/ui/Message.kt:61–75`：相邻图片合并；`:414`：Image part 定义。
- 当前 `ai/src/main/java/me/rerere/ai/provider/providers/OpenAIProvider.kt:217–356`：独立生图；`:238–244`：只对单图启用该流式路径；`:358–420`：独立编辑。
- 官方 `ai/src/main/java/me/rerere/ai/provider/providers/openai/ResponseApiStreamDecoder.kt:85–135、169–177`：按 ID 开始、partial snapshot、最终快照与结束；`:264–279、334–340、395–412`：流状态和收尾。
- 官方 `ai/src/main/java/me/rerere/ai/provider/providers/openai/ResponseAPI.kt:326–330`：官方模型字符串。
- 当前 `app/.../data/ai/transformers/Base64ImageToLocalFileTransformer.kt:7–18`、`FilesManager.kt:187–203`：生成完成后的落盘。

### 7.3 推荐技术路线：限定范围的图片流增量

建议先在当前 `MessageChunk`/聚合机制中加入足够的图片身份与快照语义，或者用一个小型适配层将官方图片事件转换为当前能消费的内部事件。**暂不为此迁移官方整个 StreamChunk、所有 provider decoder、会话配置和消息架构。**

需要满足的状态模型：

```text
Responses SSE
  ├─ output_item.added(image_generation_call, item.id)
  │    └─ 建立该 item 的图片状态
  ├─ image_generation_call.partial_image(item_id, partial_image_b64)
  │    └─ 替换该 item 的预览快照，不追加到上一张 base64 后面
  ├─ output_item.done(item.id, item.result)
  │    └─ 用最终图替换预览，标记完成
  └─ stream error / cancel / close
       └─ 收尾未完成状态，按约定保留或清理预览
```

实施原则：

1. 以服务端图片 item ID 关联更新。`partial_image_index` 是中间阶段序号，不能当成第几张图片；也不要直接拿 function call 的 `output_index` 归一化规则代替图片身份。
2. 快照是**替换**，不是文本增量拼接。若有两个图片 item 交错更新，必须分别更新各自的图片 part。
3. 运行时聚合状态优先放在 transient 层；若必须扩展持久化 Image 字段，提供默认值并验证旧消息 JSON、导出和恢复。
4. 最终图继续通过当前 `FilesManager` 和会话文件管理保存。不为聊天内生图强制写入 GenMedia/MediaCreation 数据库。
5. 明确失败或取消时的行为：未完成预览不能伪装成成功的最终附件；临时文件清理、最后预览是否保留需一致。
6. 对不返回 partial 事件的 provider 保持兼容；只有最终结果时仍正常显示。
7. 模型和中转服务能力独立校验。不能因官方源码存在某字符串就认定账号、代理或 API Key 通道支持它。
8. 预览内存按每个 item 的最新快照保留，避免每帧 base64 都进入消息历史。必要时限制 UI 更新频率，并测量大图生成时的内存。

### 7.4 如果希望聊天工具调用独立 Images API

这是可选扩展，不是完善 Responses 的前提。当前 `ImageGenerationTool` / `draw_image` 已有基础，适合从现有实现解耦：

```text
聊天工具参数 / 用户参考图
  → 当前 Provider.generateImage / editImage
  → 中间预览回调（如通道支持）
  → 最终图写入聊天文件
  → UIMessagePart.Image / 工具结果
```

- 保留当前 `/images/generations` 的单图流式逻辑；多图目前走非流式，避免误用 partial 阶段序号作为图片编号。
- `/images/edits` 继续使用已验证的本地文件 multipart：单图字段 `image`，多图 `image[]`。不同服务商是否接受这些字段需分别测试。
- Responses 的会话输入 `input_image` 与独立编辑 multipart 是两套协议；把参考图放进聊天上下文，不等于独立编辑请求已复用它。
- 可按需求参考官方 OpenRouter `input_references` 分支与编辑测试，但要由 provider 能力选择路径。
- 将“保存到图库”与“把图片作为聊天附件返回”分开，避免 `GenMediaRepository` 成为聊天生图的必需依赖。
- 现有旧 ImgGen 的图库保存行为保持原样；本轮不迁入新的媒体中心。

### 7.5 文件级工作清单

| 官方参考 | 当前落点 | 本轮改动 |
|---|---|---|
| `ResponseApiStreamDecoder.kt` 的 image 分支与状态管理 | `ResponseAPI.kt` + 当前消息聚合层 | partial 事件、item ID、快照替换、完成/中断收尾 |
| `StreamChunk` 图片事件设计 | `MessageChunk` / `Message.kt` 对应模型 | 做最小兼容扩展，不全量替换所有流事件 |
| 官方 provider 图像编辑测试 | 当前 `ai` provider 测试 | 补通道差异、参考图和异常回归 |
| 官方图片结果处理思路 | 当前 `Base64ImageToLocalFileTransformer` / `FilesManager` | 最终图去重落盘、失败/取消清理 |
| 官方工具显示模式 | 当前 `ChatMessage` / 工具 UI | 原位更新预览，保留当前函数图和其他消息渲染 |

### 7.6 GPT Image 验收用例

- 单图：start → 多次 partial → final，只保留一张最终图，预览原位更新。
- 双图：两个 item 交错到达，互不拼接、覆盖或错位。
- 无 partial：只返回最终图仍可成功。
- 异常：错误响应、畸形/空 base64、流提前断开、只有 start 没有 final。
- 取消：预览显示后停止生成，不遗留持续生成状态，不把未完成预览当完成结果。
- 历史：重启、消息分支切换、导出、备份恢复后最终图片仍可访问。
- 通道：Responses 内建工具、独立 Images API、支持的中转服务分别测；账号通道按能力测试。
- 参考图：单图/多图编辑，文件不存在、格式不支持、HTTP 错误。
- 性能：大图、多次 partial、多图交错，检查内存增长和 UI 卡顿。

现有 `ImageGenerationProgressTest`、`ImageReferencesTest` 主要覆盖本地生图工具，不能代替 Responses 的端到端图片流回归。

## 8. Phone-use 迁移方案（仅 GitHub 渠道）

### 8.1 官方能力与前置条件

官方支持动作：`observe`、`screenshot`、`tap`、`long_press`、`swipe`、`scroll`、`type`、`press`、`open_app`、`list_apps`、`wait`。

- 服务声明、实现和专属资源位于 `app/src/github/`。
- 基础 `PhoneController` / `PhoneUseManager` / `PhoneUseTool` / `PhoneUseToolUI` 位于 `src/main`。
- 支持条件为非 Play 且 Android 11 / API 30 及以上；当前 app 最低 SDK 为 26，因此低版本需要可预测地隐藏或禁用。
- 用户需在系统设置中启用无障碍服务；每个 Assistant 另有 `localTools` 中的 `PhoneUse` 开关。
- 官方在启用和执行时还检查聊天后台浮窗及其 overlay 权限。
- 手势轨迹使用服务自己的不可触摸无障碍覆盖层。它与聊天浮窗是两种覆盖层，不能误报为手势指示器本身需要额外申请普通悬浮窗权限。

**“仅 GitHub”准确含义：** Play 不包含该服务的 GitHub source-set 实现和 Manifest 声明，也不应注册工具；共享工具代码仍参加 main 源码编译，最终是否被 R8 删除要看产物。不能声称官方 Play 完全没有任何 Phone-use 相关字节码。

### 8.2 坐标和动作语义

| 项目 | 官方行为 | 迁移注意 |
|---|---|---|
| 模型坐标 | **0–1000 网格** | 不是 0–100；参数说明与执行公式必须一致 |
| 执行坐标 | `PhoneScreen.width/height` 对应物理屏幕像素 | 不与 dp、窗口局部坐标混用 |
| 网格越界 | 输入夹取到允许范围 | 测边界；右/下边界最终是否落到有效像素要核对 |
| 元素定位 | 最新一次读屏的元素索引 | 页面改变后旧索引可能失效，不缓存跨页面复用 |
| 截图 | JPEG，最大边长 1568 | 模型看到的图已缩放，需一致映射回物理屏幕 |
| `tap` / `long_press` | 元素索引或网格坐标 | 校验缺失参数、无效元素 |
| `swipe` | 起点元素/坐标，终点 `to_x/to_y` | 校验长度、方向和屏幕范围 |
| `scroll` | up/down/left/right，可指定元素 | 目标区域与全屏滚动要分开 |
| `type` | 文字、可选元素；可选 submit | 聚焦失败/不可编辑时返回可理解错误 |
| `press` | Back/Home/Recents/Notifications/Enter | 不应任意接受未定义按键 |
| `wait` | 默认 2 秒，夹取 0.5–10 秒 | 不能成为无限等待路径 |

官方 schema 仅将 `action` 标为 required，其余条件主要在执行期校验。移植时应保留动作级参数检查，不仅复制 JSON schema。

### 8.3 需要完整接入的执行链

```text
GitHub flavor + API 30+
  → Assistant 开启 PhoneUse
  → 系统无障碍服务连接 + 当前应用所需浮窗设置有效
  → LocalTools.getTools 注册 phone_use
  → 当前聊天工具循环调用 PhoneUseTool
  → PhoneUseManager / PhoneController
  → GitHub PhoneUseAccessibilityService
       ├─ 读屏 / 截图
       ├─ 手势 / 输入 / 系统按键
       └─ GestureIndicator
  → FilesManager 保存截图 + 结构化工具结果
  → 现有 ToolUIRegistry 显示 PhoneUseToolUI
```

### 8.6 停止能力必须作为发布条件

源码链路显示：官方 `ChatFloatingWindows.kt:179–195` 的 Stop 可调用 `ChatService.stopGeneration`；但同文件 `:111–128` 在 `manager.acting=true` 时把 bubble/panel 透明化并禁触摸。工具在截图和手势等操作中设置 acting，因此存在用户暂时点不到该 Stop 的窗口。官方所查通知实现也未找到独立 Stop action。

建议在当前应用中实现：

1. 以当前生成取消机制为唯一取消源，连接到工具 Session/管理器。
2. 提供操作期间仍可到达的停止入口，例如与生成任务绑定的前台通知 Stop；若使用独立控制层，需保证不被全局 acting 隐藏且不会拦截目标手势。
3. 每个操作提交前检查取消状态；取消后不排队下一动作。
4. 对已交给 Android 的手势，依据平台实际支持处理取消/替换或等待回调，不能向用户承诺协程取消能瞬间撤回已执行点击。
5. 超时、取消、截图错误、服务断开、应用退后台等路径都在 `finally` 恢复 acting、窗口和工具状态。
6. 多个聊天会话同时启用时，通过管理器确保只有一个执行者控制屏幕，避免会话级 Mutex 之间互不相识。

当前已有后台生成服务，新增通知 action 时先核对其现有停止能力并复用，不直接照搬官方通知类。

### 8.7 设置、备份与旧版本兼容

`LocalToolOption` 是序列化 sealed 类型，PhoneUse 保存到 `Assistant.localTools`。**仅添加工具选项不需要新增 Room 表**，但需要处理 JSON 和版本边界：

- 默认关闭；旧设置没有该选项时正常读取。
- 新设置保存、应用重启、备份恢复后该选项保持一致。
- Play / API 26–29 即使导入启用该项的备份，也不能注册执行工具。
- 旧版本不认识新的 sealed subtype，可能反序列化失败。`ignoreUnknownKeys` 不能自动保证未知多态类型可读。
- 回滚前保留未包含 PhoneUse 的设置备份；如提供兼容导出，明确移除不受旧版支持的选项。
- 反序列化成功不代表已授权；恢复备份不能代替系统无障碍授权和运行时检查。
