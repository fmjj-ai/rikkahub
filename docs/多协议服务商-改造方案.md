# 多协议服务商（中转站）改造方案

> 版本：v0.1（待评审）｜适用：当前工作区 RikkaHub
> 性质：设计方案，不含实现代码
> 一句话：把「协议」从服务商类型里拆出来，变成一个服务商下三个默认都可用的协议配置；模型记住自己走哪个协议。

---

## 0. 结论先行

**可行，推荐「服务商内嵌协议配置 + 模型带 protocol 字段」的方案。**

- AI 模块的三个 Provider 实现不用改。运行时把多协议服务商按模型协议解析成现有的 OpenAI / Claude / Google 配置，再走原来的请求链路。
- 一个服务商 = 一个中转站：一个名字、一份共享 URL、一份模型列表、三个协议页签；每个协议独立 Key，三个协议默认都可用。
- 拉模型按「来源协议」归属，不做模型名匹配；模型设置里可手动切协议。
- 旧配置完全兼容：旧三种类型照常读、照常跑；非内置服务商在**编辑保存时**升级为多协议；内置服务商不升级。
- 规模预估：约 6–8 人日；风险中等，主要风险是「漏改模型 → 服务商解析点」和「新 JSON 旧版本无法降级读取」。

### 0.1 与需求的对应

| 你的要求 | 方案 |
|---|---|
| 同一个站的不同模型，不用新建服务商 | 一个 `MultiProtocol`，三个协议页签 |
| 同一个服务商的不同协议，可用不同 API Key | 每个协议一份独立 `apiKey` |
| 同一个 Key 也可跨协议使用 | 不校验、不强制，允许相同 Key |
| 拉取模型时自动匹配协议 | 从哪个协议拉到，就给模型标哪个协议 |
| 模型设置里可手动选协议 | 模型编辑弹层增加「协议」选择 |
| 不按模型名强制匹配（claude 模型也可以走 OpenAI 协议） | 不做 `claude-* → Claude` 的推断 |
| 风格和原来一致 | 复用 SegmentedButton / Switch / OutlinedTextField / Card / Tag / ModalBottomSheet |

### 0.2 本轮已确认（以此为准）

| # | 事项 | 你的选择 / 我的理解 |
|---|---|---|
| 1 | 旧服务商升级时机 | 编辑保存时升级；不做启动全量迁移 |
| 2 | 同一模型多协议可拉取 | 按协议分组，各加一份 |
| 3 | 合并同 URL 时同协议 Key 冲突 | 弹窗由你选保留哪个；不自动合并 Key |
| 4 | `providerOverwrite` | 保留，优先级最高 |
| 5 | URL | **服务商级共享一个 Base URL**；Google 页签保留，但不做 `/v1beta` 适配（你说主要用 OpenAI / Claude） |
| 6 | 协议启用 | 三个协议默认全部可用，**不设「启用此协议」开关**；没填 Key 视为未配置：拉模型跳过，模型设置仍可选但提示 |
| 7 | 同 URL 旧服务商 | 检测到后提示，手动合并；不自动删数据（见 7.8） |

> 第 5、6 条是我根据你「谷歌不用适配」「协议默认全部启用」的理解整理的；如果你其实想要「每协议独立 URL / 独立开关」，告诉我，我再调。
> 下文是详细设计；与本节冲突时以本节为准。

## 1. 现状盘点

### 1.1 协议 = 服务商类型

`ProviderSetting` 是一个 sealed class，三个子类各自带 `apiKey`、`baseUrl` 和协议特有开关：

- [`ProviderSetting.kt`](../ai/src/main/java/me/rerere/ai/provider/ProviderSetting.kt)：`OpenAI` / `Google` / `Claude`
- [`ProviderSetting.Types`](../ai/src/main/java/me/rerere/ai/provider/ProviderSetting.kt)：就是这三个类
- 配置页顶部 SegmentedButton 切换的是**类**，`convertTo()` 会造一个不同类型的新对象，协议特有字段会丢（Response API、Prompt Caching、Vertex 等）

所以现在「一个站想用两种协议」只能建两个服务商。

### 1.2 Key / URL 在服务商上，模型只有整体覆盖

- [`Model.kt`](../ai/src/main/java/me/rerere/ai/provider/Model.kt)：`Model` 本身没有协议字段，只有 `providerOverwrite: ProviderSetting?`
- `providerOverwrite` 可以给单个模型覆盖**整个**服务商配置，但没法「只换协议，沿用本站 Key/URL」，也不能在一个站下统一管理多协议模型

### 1.3 模型协议只能由所属服务商决定

- [`PreferencesStore.kt`](../app/src/main/java/me/rerere/rikkahub/data/datastore/PreferencesStore.kt) 的 `Model.findProvider()` 找到所属服务商
- [`ProviderManager.kt`](../ai/src/main/java/me/rerere/ai/provider/ProviderManager.kt) 的 `getProviderByType()` 按类分发
- 全仓约 12 处这样取 Provider：聊天、标题、建议、压缩、翻译、OCR、生图、余额、测连接、拉模型

### 1.4 可以复用的东西

| 能力 | 位置 | 用途 |
|---|---|---|
| 三个协议实现 | `ai/.../providers/` | 运行时只需喂一个 typed setting |
| 模型级覆盖 | `Model.providerOverwrite` | 保留为更细粒度的「单模型专用配置」 |
| URL 版本转换 | [`ProviderConfigure.kt`](../app/src/main/java/me/rerere/rikkahub/ui/pages/setting/components/ProviderConfigure.kt) 的 `convertTo()` | 新协议 URL 自动预填（`/v1` ↔ `/v1beta`） |
| 多 Key 轮询 | `KeyRoulette` | 每个协议独立 Key 直接复用 |
| 多态分享 | [`ShareSheet.kt`](../app/src/main/java/me/rerere/rikkahub/ui/components/ui/ShareSheet.kt) | 新类型直接参与 QR / 备份序列化 |

### 1.5 为什么不按模型名推断协议

同一个中转站经常用 OpenAI 协议转发 Claude / Gemini 模型；`claude-*` 不代表必须走 Claude 原生协议。按名字匹配会违背「中转站做适配」的场景，也和你要手动切换的诉求冲突。

## 2. 目标 / 非目标

### 2.1 目标

1. 新建/编辑一个服务商，三个协议（OpenAI / Google / Claude）默认都可用；服务商级共享一个 Base URL，每个协议独立 Key 和协议特有选项。
2. 模型列表属于服务商一份；每个模型带一个「协议」归属。
3. 拉模型：聚合并标记来源协议；按协议分组；某个协议失败不影响其它协议。
4. 模型设置：可切换协议；切换不影响模型其它字段；未配置协议给出提示但不强制回改。
5. 聊天 / 标题 / 建议 / 压缩 / 翻译 / OCR / 生图 / 余额 / 测连接按模型协议路由。
6. 旧配置、旧备份、旧二维码尽量兼容；内置服务商不变。

### 2.2 非目标

- 不按模型名/前缀推断协议。
- 不强制同 Key、不校验模型名与协议是否匹配。
- 不支持「同模型同协议多份配置」（同模型不同协议可以）。
- 不重写三个 Provider 实现，不新增网络协议。
- 不改内置服务商（RikkaHub / AiHubMix / DeepSeek / 月之暗面…）。
- 首期不做 CherryStudio / Chatbox 导入器到多协议的转换。

## 3. 数据模型

### 3.1 协议枚举

```kotlin
@Serializable
enum class ProviderProtocol {
    @SerialName("openai") OPENAI,
    @SerialName("google") GOOGLE,
    @SerialName("claude") CLAUDE,
}
```

顺序与现有页签一致：OpenAI / Google / Claude。

### 3.2 Model 增加协议字段

```kotlin
@Serializable
data class Model(
    // ...原有字段
    /**
     * 多协议服务商下，这个模型走哪个协议。
     * null = 跟随服务商的 defaultProtocol（兼容旧数据、typed 服务商忽略此字段）。
     */
    val protocol: ProviderProtocol? = null,
)
```

语义：

- 旧的 typed 服务商：字段为 null，运行时按服务商类型走，行为完全不变。
- 多协议服务商：拉模型、转换、手动添加时写入明确协议；手动切换时改这个字段。
- 同一个 `modelId` 允许在不同协议下各存在一份（`id` 仍然唯一）。

### 3.3 新增多协议服务商类型

```kotlin
@Serializable
@SerialName("multi")
data class MultiProtocol(
    override var id: Uuid = Uuid.random(),
    override var enabled: Boolean = true,
    override var name: String = "New Provider",
    override var models: List<Model> = emptyList(),
    override val balanceOption: BalanceOption = BalanceOption(),
    @Transient override val builtIn: Boolean = false,
    @Transient override val description: @Composable (() -> Unit) = {},
    @Transient override val shortDescription: @Composable (() -> Unit) = {},
    val baseUrl: String = "",
    val defaultProtocol: ProviderProtocol = ProviderProtocol.OPENAI,
    val openai: ProviderSetting.OpenAI? = null,
    val google: ProviderSetting.Google? = null,
    val claude: ProviderSetting.Claude? = null,
) : ProviderSetting() {
    // addModel / editModel / delModel / moveMove 都操作父级 models
    // copyProvider 负责 id/name/models/balanceOption 等公共字段
}
```

设计说明：

- **复用现有三个 typed setting 作为协议配置**，不重写一套字段。这样 Vertex、Prompt Caching、Response API、API 路径、多 Key 等能力零成本保留。
- 协议配置里的 `models` 恒为空，模型统一放父级；`id` / `name` 在解析时用父级覆盖，避免脏数据。
- `balanceOption` 放父级；只有 OpenAI 协议支持余额查询，解析 OpenAI endpoint 时把父级的 `balanceOption` 带过去。
- `description` / `shortDescription` 仍是 `@Transient`，内置服务商不参与升级，不影响现有描述逻辑。
- 服务商级共享一个 `baseUrl`（你主要用 OpenAI / Claude，两者同一地址即可）；解析 endpoint 时统一使用父级 URL。Google 页签保留，但不做 `/v1beta` 适配。
- 每个协议的 typed 配置里仍保留 `baseUrl` 字段，落库/解析时同步为父级值，避免旧逻辑读不到；未来若需要 Google 原生协议，再单独加「协议级地址覆盖」。
- 协议不再单独设启用开关：三个协议默认都可用，UI 不暴露 `enabled`；没填 Key 视为「未配置」，拉模型跳过，运行时若被模型选中则给明确提示。

JSON 形态（示意）：

```json
{
  "type": "multi",
  "id": "...",
  "enabled": true,
  "name": "万物",
  "baseUrl": "https://www.aiwanwu.cc/v1",
  "defaultProtocol": "openai",
  "openai": {
    "type": "openai",
    "apiKey": "sk-...",
    "baseUrl": "https://www.aiwanwu.cc/v1",
    "chatCompletionsPath": "/chat/completions",
    "useResponseApi": false,
    "includeHistoryReasoning": true,
    "models": []
  },
  "claude": {
    "type": "claude",
    "apiKey": "sk-...",
    "baseUrl": "https://www.aiwanwu.cc/v1",
    "promptCaching": false,
    "models": []
  },
  "models": [
    { "id": "...", "modelId": "claude-sonnet-4-5", "protocol": "claude" },
    { "id": "...", "modelId": "gpt-4o", "protocol": "openai" }
  ]
}
```

### 3.4 解析规则

```kotlin
fun Model.resolveEndpoint(providers: List<ProviderSetting>): ProviderSetting? {
    // findProvider 已包含 providerOverwrite 优先级
    val provider = findProvider(providers, checkOverwrite = true) ?: return null
    return if (provider is ProviderSetting.MultiProtocol) {
        provider.endpointOrNull(protocol ?: provider.defaultProtocol)
            ?.takeIf { it.isConfigured() }
    } else {
        provider
    }
}
```

优先级从高到低：

1. `model.providerOverwrite`（旧逻辑，保持最高优先级）
2. `model.protocol`
3. `provider.defaultProtocol`（仅 Multi）
4. typed 服务商自身类型

约束：

- endpoint 为 null 或「未配置」（Key 为空；Google 可用 Service Account）时**不静默回退**到别的协议，抛/返回带「服务商名 + 协议名」的错误，避免用户以为在用 Claude 实际走了 OpenAI。
- 解析时统一规范化 endpoint 的 `id` / `name` / `models`，保证 KeyRoulette、日志、分享里的信息一致。

### 3.5 辅助 API

| API | 作用 |
|---|---|
| `MultiProtocol.endpoint(protocol)` | 取某个协议的 typed 配置（未配置返回 null） |
| `MultiProtocol.configuredProtocols()` | 已填 Key 的协议列表，用于列表标签、拉模型 |
| `Model.effectiveProtocol(owner)` | 模型实际使用的协议（含 null 回退） |
| `ProviderSetting.toMultiProtocol()` | typed → Multi，保留 id/name/enabled/models，并把已有模型显式写入协议 |
| `Model.selectionKey()` | `modelId to protocol`，用于添加/取消模型时的去重 |
| `ProviderSetting.isMultiProtocol` | 便于 UI 判断 |

## 4. UI 方案

### 4.1 服务商列表

复用现有 Card，只在标签行增加已配置协议：

```
┌──────────────────────────────────────────┐
│ [icon] 万物                        ⠿     │
│        OpenAI · Claude                   │
│        [已启用] [模型 12] [OpenAI] [Claude] │
└──────────────────────────────────────────┘
```

- 协议标签用 `TagType.INFO`，跟现有「模型数」标签同一行 FlowRow。
- 三个协议都没填 Key 时显示 `TagType.WARNING`「未配置协议」。
- 卡片点击、拖拽、启用状态、删除逻辑都不变。

### 4.2 配置页

保留底部「配置 / 模型」两个页签和顶部返回/分享，不改导航。

```
┌─────────────────────────────────────────────┐
│ <  万物                                  ⤴  │
├─────────────────────────────────────────────┤
│ 名称      [ 万物                        ]   │
│ API Base Url [ https://www.aiwanwu.cc/v1 ]  │  ← 服务商级共享
│ 启用服务商                        [ ON ]    │
│                                             │
│ [ OpenAI ✓ | Google | Claude ]              │  ← 协议页签，三个默认都可用
│                                             │
│ ── OpenAI 协议 ───────────────────────────  │
│ API Key   [ •••••••••••••••       👁 ]      │
│ API 路径  [ /chat/completions            ]  │
│ Response API                      [ OFF ]   │
│ 回传历史思考过程                  [ ON ]    │
│                                             │
│ [测试连接]               [重置地址] [保存]  │
└─────────────────────────────────────────────┘
```

关键交互：

- **顶部 Segmented 仍是三段**，视觉不变；语义从「切换服务商类型」变成「切换协议页签」，三个协议默认都可用，不设「启用此协议」开关。
- 名称、共享 Base URL、服务商级启用开关放在页签外，三个协议共享。
- 每个页签内只有 Key 和协议特有字段：OpenAI 的路径 / Response API / 历史思考，Claude 的缓存，Google 的 Vertex。
- **Google 页签保留，但不做 `/v1beta` 适配**：共享 URL 直接用于三个协议；你主要用 OpenAI / Claude，Google 没填 Key 就不会拉模型、不会打扰。
- 没填 Key 的协议视为「未配置」：拉模型跳过；模型设置里仍可选，但会提示。
- 旧的非内置 typed 服务商：打开配置页时在内存里 `toMultiProtocol()`，保存时写回 Multi。用户只要切到 Claude 页签、填 Key、保存，就完成升级，不用重建服务商。
- 内置服务商：保持旧 UI，不升级。
- 模型级 `providerOverwrite` 编辑器：保持 typed UI（它本身就是「单协议配置」）；新增覆盖时用模型当前协议的 endpoint 初始化，避免生成一个 Multi 覆盖。
- 添加服务商弹窗内容会比现在高（多了协议页签），必要时把弹窗内容改成可滚动或改用底部弹层；配置页本身已经是 `verticalScroll`，不受影响。

### 4.3 模型页

```
┌──────────────────────────────────────────┐
│ [icon] claude-sonnet-4-5                 │
│        [Claude] [Chat] [Text] [Tool]     │
└──────────────────────────────────────────┘
┌──────────────────────────────────────────┐
│ [icon] gpt-4o                            │
│        [OpenAI] [Chat] [Text] [Reasoning]│
└──────────────────────────────────────────┘
```

- 模型卡片标签行最前面加协议 Tag（仅 Multi 显示）。
- 协议没填 Key 时追加 `TagType.WARNING`「Claude 未配置」，但不隐藏模型。
- 模型排序、滑动删除、拖拽、编辑逻辑不变。
- 聊天输入框/全局模型选择器（`ModelList.kt`）里，同一服务商下可能出现同名不同协议的模型，建议同样显示协议 Tag，避免选错。

### 4.4 添加模型

```
可用模型                      [全部添加 12] [刷新]
── OpenAI 协议 (8) ─────────────────────────
 gpt-4o                              [+]
 claude-sonnet-4-5                   [+]
── Claude 协议 (4) ─────────────────────────
 claude-sonnet-4-5                   [+]
 claude-opus-4-1                     [+]
── Google 协议 ─────────────────────────────
 ⚠ 拉取失败：401 Unauthorized
[筛选...]
```

- 按协议分组；每组标题带数量。
- 每行带来源协议 Tag；「已添加」按 `(modelId, protocol)` 判断，同模型不同协议可以各加一份。
- 某个协议失败只在该组显示错误摘要，其它组正常；可选手动刷新。
- 只拉取已填 Key 的协议；没填 Key 的协议不显示分组，也不发请求。
- 手动「添加模型」默认协议 = 当前服务商第一个已配置协议；之后可在模型设置里改。

### 4.5 模型编辑

```
模型 ID    [ claude-sonnet-4-5 ]   （编辑时只读）
名称       [ claude-sonnet-4-5 ]
协议       [ OpenAI | Claude ✓ | Google ]     ← 仅多协议服务商显示
模型类型   [ Chat | Embedding | Image ]
输入模态   [ Text | Image ] ...
```

- 协议选择用现有 `SingleChoiceSegmentedButtonRow`，与模型类型/能力选择器风格一致。
- 选中未填 Key 的协议：允许保存，但下方显示警告「Claude 协议未填 Key，发送请求会失败」。
- 如果模型有 `providerOverwrite`：显示「已使用独立服务商覆盖，协议选择不生效」。
- 模型类型与协议的能力约束（建议）：
  - `IMAGE`：目前只有 OpenAI 协议实现，其它协议置灰或警告；
  - `EMBEDDING`：OpenAI / Google 可用，Claude 警告；
  - `CHAT`：三个都可用。

### 4.6 其它入口

| 入口 | 处理 |
|---|---|
| 测连接 | 按测试模型解析协议；结果标题带协议名 |
| 余额 | 仅 OpenAI；Multi 下取 OpenAI endpoint，UI 位置不变 |
| 生图 | 按 IMAGE 模型协议路由；非 OpenAI 给明确错误 |
| OCR / 压缩 / 翻译 / 标题 / 建议 | 按各自模型的协议路由 |
| 聊天顶栏 | 仍显示父级服务商名「万物」，不显示协议 |
| 文件选择器 | 当前模型协议为 Google 时才显示视频/音频入口 |
| 分享二维码 | 整个 Multi（含各协议 Key）一起分享 |

### 4.7 风格一致性

- 不新增页面层级，仍是「配置 / 模型」两个底部页签。
- 复用现有组件：`SingleChoiceSegmentedButtonRow`、`OutlinedTextField`、`Switch`、`Card`、`Tag`、`ModalBottomSheet`、`SecondaryTabRow`。
- 协议标签统一 `TagType.INFO`，警告统一 `TagType.WARNING`。
- 不引入新的主题色、圆角、间距体系。

## 5. 拉模型的协议归属

### 5.1 流程

```kotlin
// 伪代码
val results = configuredProtocols.map { protocol ->
    protocol to runCatching {
        providerManager.getProviderByType(endpoint(protocol))
            .listModels(endpoint(protocol))
            .map { it.copy(protocol = protocol) }
    }
}
```

- 只拉取已填 Key 的协议；三个都没填时展示手动添加提示。
- 各协议并发拉取（`async`）；单个失败不影响其它。
- 返回模型统一写入 `protocol`，供分组和添加使用。
- 同一个 `modelId` 在不同协议都返回：分别保留（分组不同），不做名字合并。
- 同一个协议内重复 `modelId`：去重。

### 5.2 失败处理

- 失败组显示简短原因（HTTP code / message），不阻断其它组。
- Claude / Google 的 `/models` 在部分中转站不可用；此时仍可手动添加模型并选协议，不把「拉不到」当成「不能用」。
- 可选：分组标题右侧加刷新按钮，刷新只重拉该协议。

### 5.3 选择状态

- 「已添加」判断统一用 `(modelId, protocol)`，不要只用 `modelId`。
- 「全部添加 / 全部取消」按同样的 key 去重。
- 服务商模型列表的拖拽 key 仍是 `Model.id`，同 `modelId` 不同协议不会冲突。

## 6. 运行时链路改造

### 6.1 总图

```
用户选中的 Model
   │
   ├─ model.providerOverwrite != null ──→ 直接用该 typed 配置（旧逻辑）
   │
   └─ findProvider(providers) ──→ MultiProtocol
            │
            ├─ model.protocol ?: defaultProtocol
            │
            └─ endpointOrNull(protocol)
                     │
                     ├─ null / 未配置 Key ──→ 明确报错（服务商名 + 协议名）
                     │
                     └─ typed endpoint（OpenAI / Claude / Google）
                              │
                              └─ ProviderManager.getProviderByType(endpoint)
                                       │
                                       └─ 原来的 generateText / streamText / listModels ...
```

### 6.2 改造点

| 位置 | 现状 | 改法 |
|---|---|---|
| `GenerationHandler.generateText` | `findProvider` → `getProviderByType` | 先用 `resolveEndpoint`，再分发 |
| `GenerationHandler.translateText` | 同上 | 同上 |
| `GenerationHandler` 里 `provider is Claude / OpenAI` | 判断服务商类型 | 改为判断 endpoint 类型（协议） |
| `ChatService.generateTitle` | 同上 | 同上 |
| `ChatService.generateSuggestion` | 同上 | 同上 |
| `ChatService.compactMessages` | 同上 | 同上 |
| `OcrTransformer` | 同上 | 同上 |
| `ImageGenerationTool` | 同上 | 同上 + 非 OpenAI 明确报错 |
| `ImgGenVM`（2 处） | 同上 | 同上 |
| `ProviderConnectionTester` | 直接 `getProviderByType(internalProvider)` | 先解析模型协议 endpoint |
| `ProviderBalanceText` | 接收 OpenAI typed | Multi 下传 OpenAI endpoint |
| `SettingProviderDetailPage.ModelList` | 单次 `listModels` | 多协议并发 + 分组 |
| `FilesPicker` | `provider is Google` | 当前模型 endpoint 是 Google |
| `ChatPage` 顶栏 | 显示服务商名 | 保持父级名，不改 |
| `LocalTools` 生图可用性 | 只判断 provider 非空 | 保持；可选加协议检查 |

### 6.3 错误文案

建议新增：

- 「服务商「%1$s」未填写 %2$s 协议的 Key，请在 设置 → 服务商 → %1$s → 配置 中填写」
- 「模型「%1$s」使用的 %2$s 协议未配置」
- 「拉取 %1$s 协议模型失败：%2$s」

后台调用（标题/建议/压缩）沿用现有错误捕获，但错误信息要能看出是协议问题，而不是笼统的「Provider not found」。

### 6.4 防呆

- `ProviderManager.getProviderByType(MultiProtocol)` 直接抛 `error("Multi protocol provider must be resolved to an endpoint")`，漏改的调用点会在开发/测试期立刻暴露。
- 单测覆盖：typed 旧数据、Multi 显式协议、null 协议回退、协议未配置 Key、协议缺失、`providerOverwrite` 优先级。
- 合并前全局搜索 `getProviderByType(`，逐个确认入参已经是 endpoint。

## 7. 兼容与迁移

### 7.1 旧数据

- 旧的 OpenAI / Google / Claude 服务商继续可读、可跑；运行时走原分支，不需要迁移。
- 旧备份、旧二维码导入后仍是 typed，正常工作。
- `Model.protocol` 对旧模型为 null，不会改变行为。

### 7.2 升级时机（推荐：编辑时升级）

- 不做启动时全量迁移，降低回滚风险。
- 非内置 typed 服务商打开配置页 → 内存中 `toMultiProtocol()` → 保存时落库为 Multi。
- 内置服务商不升级，避免破坏默认 URL、描述、余额等逻辑。

### 7.3 新建

- 顶部「+」默认创建 Multi，三个协议默认都可用，OpenAI 页签默认选中。
- 旧的单类型添加方式不再作为默认入口；模型级覆盖编辑器仍可创建 typed 配置。

### 7.4 分享 / 备份

- `MultiProtocol` 用 `@SerialName("multi")` 参与多态序列化；二维码、备份、WebDAV/S3 都能带三个协议。
- 旧版本 App 遇到 `type: "multi"` 会解码失败：分享给旧版本时提示「对方版本不支持多协议」，不静默丢配置。
- 分享二维码仍包含 Key，保持现有安全提示。

### 7.5 导入器

- CherryStudio / Chatbox 首期仍导入为 typed，不强制转 Multi。
- 它们的 `when (provider)` / `providerTypeName()` 需要补 Multi 分支，避免编译失败或运行崩溃；可以先取「第一个已配置协议」做近似映射。

### 7.6 providerOverwrite

- 优先级最高，保持旧行为。
- Multi 下新增覆盖时，用模型当前协议 endpoint 初始化，得到 typed 覆盖；不要生成 Multi 覆盖。
- 模型设置里如果已有覆盖，协议选择置灰并提示不生效。

### 7.7 降级

- 新版本写出的 Multi 旧版本无法读取；这是新增多态类型的固有代价。
- 建议在发布说明里提醒：升级前导出备份；降级前先导出，或删除多协议服务商。

### 7.8 合并同 URL 旧服务商（新增）

你之前的用法是「同一个 URL 建了多个服务商」，升级后不需要手动重建：

- **检测**：对非内置服务商的 `baseUrl` 归一化（协议/主机小写、去尾斜杠；`/v1` 与 `/v1beta` 视为同一站点）后分组；在服务商列表顶部提示「检测到 N 个相同地址的服务商，可合并」，不自动改动。
- **入口**：提示条 + 每个卡片的「合并到…」；你指定主服务商。
- **合并规则**：
  - 每个来源按原类型落到对应协议（OpenAI→openai、Claude→claude、Google→google）；
  - 模型全部并入主服务商，协议取来源服务商类型；
  - 各协议的 Key、协议特有选项保留；共享 URL 用主服务商的地址；
  - 名称、图标、排序、启用状态、余额选项用主服务商；
  - 同 `modelId` 同协议去重；同 `modelId` 不同协议保留两份；
  - 确认框列出「将合并哪些、会删哪些」，确认后才删除被合并条目。
- **冲突**：同一协议出现两个不同 Key 时，弹窗让你选保留哪个（你已确认）；不选就保留原样、不合并。两个 Key 都合法但你想轮询，可选「两个都保留，用 KeyRoulette 轮询」作为备选。
- **同 URL 同协议的多份**（例如两个 OpenAI Key 不同）默认不自动合并，避免额度/权限混淆。
- **不做**：不自动合并、不自动删除、不碰内置服务商；旧 typed 服务商即使不合并也继续能跑。
- 合并前可先导出备份；合并完成后在同一个 Multi 里继续加协议/模型。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 漏改模型 → Provider 解析点 | 走错协议或崩溃 | 集中到 `resolveEndpoint`；`ProviderManager` 防呆；全局搜索 + 单测 |
| 旧 typed 判断（`is OpenAI` 等）漏改 | UI/功能异常 | 新增 sealed 子类会触发 `when` 编译错误；逐项 review 45 处 `is` 判断 |
| 新 JSON 旧版本无法读取 | 降级/分享给旧版失败 | 发布说明提示；分享时提示版本；必要时提供「导出为旧格式」后续再做 |
| 同模型多协议的选择状态 | 错删/错加模型 | 统一 `(modelId, protocol)` key；测试全部添加/取消 |
| Claude/Google `/models` 不可用 | 拉不到模型 | 分组失败提示；保留手动添加 + 选协议 |
| Google 原生 URL 与 OpenAI 不同 | 请求 404 | 本期不做适配（已确认）；Google 没填 Key 就不拉取；后续可加协议级地址覆盖 |
| 模型级覆盖与协议冲突 | 用户以为切了协议 | 覆盖优先级最高；UI 明确提示；新增覆盖用当前协议初始化 |
| 配置页信息密度上升 | 新用户困惑 | 默认选中 OpenAI 页签；没填 Key 的协议保持简洁提示；高级项保持原位置 |

## 12. 已确认决策

| # | 事项 | 决策 |
|---|---|---|
| 1 | 旧服务商升级时机 | 编辑保存时升级；不做启动全量迁移 |
| 2 | 同一模型多协议可拉取 | 按协议分组，各加一份 |
| 3 | 合并同 URL 时同协议 Key 冲突 | 弹窗选保留哪个；不自动合并 Key |
| 4 | `providerOverwrite` | 保留，优先级最高 |
| 5 | URL | 服务商级共享一个 Base URL；Google 页签保留、不做 `/v1beta` 适配 |
| 6 | 协议启用 | 三个协议默认都可用；不设「启用此协议」开关；没填 Key 视为未配置 |
| 7 | 同 URL 旧服务商 | 检测提示 + 手动合并；不自动删数据 |

## 13. 备选方案（为什么不选）

1. **保留三个独立服务商 + UI 分组**：数据仍是多个；切协议要搬运模型；共享模型列表、统一 Key 管理都做不了；所有 `providers` 遍历逻辑仍要改。
2. **每个协议自动创建一个隐藏服务商**：用户看到一个，底层是多个；删除、分享、备份、模型归属都要额外同步，容易出现「幽灵服务商」。
3. **只加 `Model.protocol` + `Map<Protocol, Credentials>`**：需要重写一套协议配置字段（Vertex、缓存、Response API、路径、多 Key），等于把现有 typed setting 再实现一遍，维护成本更高。
