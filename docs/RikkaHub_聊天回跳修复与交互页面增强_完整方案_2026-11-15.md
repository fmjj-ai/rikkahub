# RikkaHub 聊天回跳修复与交互页面增强完整方案

日期：2026-11-15  
依据：当前工作区源码与用户提供的截图。  
文档性质：一次性完整实现方案，覆盖全部交互、状态、异常与兼容边界。本次仅交付方案及记录协作偏好，尚未修改应用实现。

## 可行性结论与交付范围

**可以实现交互页面的点开查看、放大、缩小、平移和复位。** 截图中的内容来自 `rikka-viz-stream` 交互式可视化，使用原生 Compose 控件与 Canvas 绘制，不依赖 HTML 或 WebView。现有函数图已经提供全屏 Dialog、关闭和视图复位的参考实现；新增查看器可以沿用这种展示方式，继续使用原卡片的可视化会话。

全部改动作为一个完整功能集合实现：

- 修复生成结束时意外回到旧消息位置的问题，明确会话隔离、底部跟随、主动浏览及展开查看之间的滚动规则。
- 给诊断增加“填入输入框”和“复制诊断”两个入口，保留诊断原文，不添加修复提示词、代码或说明，不自动发送。
- 给交互页面增加全屏查看；图形区域支持等比缩放、平移和复位，原生按钮、滑块和输入控件继续正常使用。
- 同时处理流式生成、已有草稿、历史消息编辑、分支切换、页面尺寸变化和错误状态。

本方案没有预留“以后再补”的功能阶段。这里的“交互页面”具体指当前 `rikka-viz`、`rikka-viz-stream` 渲染体系；任意 HTML 网页或其他类型的附件不属于本次对象。放大对象是页面中的图形区域，整个交互页面通过全屏布局获得更大空间，按钮与文字输入控件维持适合触控的尺寸。

## 当前实现与问题依据

### 聊天列表

默认聊天记录使用 `ChatListNormal`，从上向下排列，以消息节点 ID 为列表项 key。生成期间存在额外的 `LoadingIndicator`；生成结束会移除它，部分配置还会显示会话系统提示项。末尾的 `ScrollBottomKey` 始终存在。

当前滚动行为有以下薄弱点：

- `ChatPage` 的初始化和发送定位使用 `currentMessages.size + 5`，生成跟随使用 `messageNodes.lastIndex + 10`，以越界余量间接表达“到末尾”。
- `isAtBottom()` 比较最后一个可见项的末端位置，没有确认它是否为真正的末项，也没有采用 `canScrollForward` 等实际边界信息。
- 自动跟随仅在生成中根据当次布局判断；没有独立保存用户是否希望继续跟随，也没有在生成完成后的最终布局更新中保持这个意图。
- 最终输出转换可能改变消息内容结构和高度；稳定的消息 key 可以维持项身份，但不会自动保证用户仍停留在新回复的末尾。
- 列表状态未在 `ChatPage` 层显式以路由会话 ID 绑定；现有导航自身已有状态隔离，不能仅据此认定发生了会话串用。

**目前没有源码证据证明生成完成会导航到另一个会话。** 已检查的完成路径主要更新消息和生成状态，没有直接跳转到旧会话的操作。因此，“上一段消息的位置回跳”与“会话路由发生切换”需要分清，不能把推测写成已经确认的根因。本方案通过统一滚动归属和定位规则消除已发现的薄弱点；若实际现象涉及路由 ID 改变，还必须在同一修复范围内处理发起该导航的调用方。

### 诊断信息

截图中的红色提示和逐行信息由 `VisualizationBlock` 展示，单条文字来自 `VizDiagnostic.summary()`。它包含已有的行号、项目 ID、字段路径和错误消息；不应在导出时额外加入当前界面未显示的 `op`、`seq` 等字段。

当前仅有“复制源码”，没有“复制诊断”或“填入输入框”。卡片还关闭了文字选择，用户不方便通过长按复制这些信息。

需要同时解决一个数据完整性问题：解析器累计统计全部诊断，但只保留最后 16 条。数量超过 16 时，仅把当前列表拼接起来会丢失前面的内容。

截图中的 `state 已声明：step` 来自重复声明，`未知流式操作：connector` 来自未支持的流式操作。`connector` 是现有图元类型，不代表同名流式操作有效。本次新增的是诊断传递能力，不通过放宽解析规则来掩盖这些错误。

### 交互查看器

`FunctionGraphCard` 已有点击画布或“放大查看”打开全屏 Dialog 的模式，但其预览与详情的手势视窗并未共享。可以参考其容器、工具栏和手势范围，不能假定直接套用便能保留交互页面的全部状态。

当前交互页面已有 `VizSessionStore`、`VizSession` 和完成求值的 frame。Canvas 目前只负责绘制，没有图元点击命中或拖动物体的能力。本次增加的是视图缩放和平移，不把平移手势解释为修改图中元件。

## 聊天回跳的完整处理

### 明确唯一的滚动归属

由 `ChatPage` 按路由会话 `id` 持有列表状态和滚动控制器。状态保存键包含会话 ID，继续配合现有 NavEntry 的保存与恢复机制；不以消息数、生成状态或末条消息 ID 作为状态重建条件。

同一个会话中，流式追加、生成完成、消息 parts 变化、系统提示项显隐都更新原列表，不重新初始化滚动位置。切换会话后，旧会话的异步定位请求不得作用于新会话。每个请求携带会话 ID 与当前定位请求版本，执行前再次确认归属；较新的用户操作可以使旧请求失效。

生成完成事件只更新其来源会话的数据与状态，不恢复旧 NavEntry，也不修改当前路由。用户已切到另一会话时，后台结果继续写回原会话，当前页面不执行其定位请求；用户主动点击会话或通知后，再按正常导航规则进入相应页面。

保留消息节点 ID 作为列表项 key，并为加载项、系统提示项和底部锚点保留各自稳定身份。不要为规避回跳而在每次生成结束时重建整个列表。

### 统一定位目标和优先级

所有到底部的操作统一定位始终存在的 `ScrollBottomKey`，使用当前列表结构算出的真实索引，并确认该索引对应的 key。目标暂未进入列表时，等待对应数据和布局版本，不再使用 `+5`、`+10` 的索引余量。

控制器区分以下意图：

- **跟随新内容**：用户位于底部、主动发送消息或点击“到底部”后，维持尾部可见。
- **浏览历史内容**：用户主动向上滚动、跳到某条消息后，保留当前消息锚点和像素偏移。
- **定位指定消息**：响应路由 `nodeId`、消息预览点击等明确请求，定位一次后转为浏览状态。
- **展开查看**：打开交互页面时暂缓背景列表的自动定位，保存来源消息和当前可见锚点。

优先级为用户当前操作、明确消息定位、仍有效的底部跟随。生成完成自身不能覆盖用户浏览历史或查看图形的意图。

### 正确判断底部与用户滚动

使用真实的列表末端信息判断已到底部；“接近底部”容差采用 dp 转换后的距离，例如 48dp，而不是固定像素。只有末尾区域已经出现时，才用真实底部锚点与有效视窗边界计算该距离，不能把普通可见消息的下边缘当成列表底部。

底部计算统一处理内容 padding、输入框 inset 和键盘导致的视窗变化，不重复扣减同一份 inset。

跟随意图独立保存。内容增长暂时把底部推到屏幕外，不能据此误判为用户停止跟随；程序发起的滚动也不能被当作用户上翻。用户拖动、鼠标滚轮、音量键上翻及定位历史消息应明确退出跟随。用户主动回到底部后重新开启跟随。

发送新消息是明确的“查看新内容”行为：消息真正进入列表后定位到底部。覆盖普通发送与“不回答”发送路径。生成中的每次内容变化只有在跟随仍有效时才调整位置，避免与用户手势争抢。

### 处理生成结束与异步高度变化

生成结束时记录当前滚动意图，在最终消息、加载项移除和系统提示项变化进入列表布局后再处理定位。

- 跟随有效：保持真实尾部可见，直到相关内容的最新布局已应用。
- 正在浏览：保持同一消息节点及原像素偏移；不要改为新回复开头、列表开头或另一条消息。
- 锚点消息因删除或分支变化消失：定位其最近的仍存在相邻消息，并夹取合法偏移；不能恢复到另一会话。
- 取消或生成失败：采用相同的最终布局规则，不把异常结束作为回顶理由。

不能只在 `loading` 从 true 变为 false 时滚动一次，也不能用固定延迟猜测布局已稳定。Markdown、图像或可视化的最终高度可能更晚变化；只要底部跟随意图仍成立，就继续依据布局更新保持末端。合并同一帧中的重复请求，目标已经可见时不再滚动，避免布局和滚动互相触发循环。

### 初始定位与预览模式

路由 `nodeId` 是一次性初始定位目标：历史数据加载完成且目标可用后再消费；目标缺失时明确退回保存位置或底部。不能因为列表暂时非空但尚未包含目标，就提前标记初始化已完成。

已有会话优先恢复该会话自己的有效浏览位置；没有可恢复位置且没有指定节点时定位底部。新建空会话等待第一批消息进入列表，不借用上一会话状态。

消息预览页继续使用自身独立列表。点击预览结果时向默认聊天列表提交按节点 ID 定位的明确请求，不把搜索预览页也改成生成跟随模式。

## 诊断原文传递的完整处理

### 界面入口与行为

在存在诊断或明确错误文案时，于诊断区提供“填入输入框”“复制诊断”两个操作；“更多”菜单提供相同入口。即使逐行诊断处于折叠状态，也能执行操作。

“填入输入框”仅编辑当前会话草稿；“复制诊断”仅写入剪贴板。两者都不触发消息发送。全屏查看器中的诊断使用相同能力；从全屏成功填入后关闭查看器并聚焦输入框，复制则保持查看器打开。

没有可导出的错误信息时不显示这些入口。仅有“正在生成可视化…”等状态提示时，不把占位文字当成诊断。

### 唯一的诊断文本格式

提取一个共用的诊断文本格式化组件，让显示、复制、填入使用同一套文案来源：

1. 对逐行诊断，第一行保留界面现有的 `部分内容未生成（N）`，后续每条使用原有 `summary()`，按产生顺序换行连接。
2. 对没有逐行诊断的静态解析错误，使用当前显示的 `result.error` 原文。
3. 不加入卡片标题、Markdown 代码围栏、源码、角色前缀、“请修复”、解释、编号或结束语。
4. 不对诊断做 trim、翻译、归纳、去重或重新措辞；换行因屏幕宽度造成的视觉折行不进入文本，诊断条目间保留真实换行。

用户截图中的内容填入后应是：

```text
部分内容未生成（8）
第2行 · state 已声明：step
第18行 · pc-bus · data · 未知流式操作：connector
第19行 · mar-bus · data · 未知流式操作：connector
第20行 · mdr-bus · data · 未知流式操作：connector
第21行 · ir-bus · data · 未知流式操作：connector
第22行 · r1-bus · data · 未知流式操作：connector
第23行 · y-bus · data · 未知流式操作：connector
第24行 · z-bus · data · 未知流式操作：connector
```

### 保留完整诊断，避免 16 条截断

将“页面默认展示数量”与“诊断留存数量”分开。在现有解析器产生诊断的位置增加记录出口，由所属 `VizSessionStore.Entry` 按处理顺序收集完整诊断；现有最近 16 条可以继续作为紧凑预览。

完整记录仅包含诊断数据，不复制每次解析的整个状态、规格或 frame。当前流式输入限制为源码 65,536 字节、单条记录 8,192 字节、非空 NDJSON 记录最多 512 条；完整诊断受这些输入预算及解析器终止条件约束。一条记录可能产生多条诊断，512 不是诊断条数或物理行数上限，不能据此再次截断导出。Entry 被替换、清除或淘汰时一并释放记录，不为每个流式 token 重建完整字符串。

记录出口必须覆盖流式记录处理、尾行处理及完成处理，并按现有已消费游标工作。同一段源码重复提交或普通重组不重复收集；同一行实际产生多条不同诊断则全部保留。源码发生非前缀替换、消息分支切换或解析会话重建时创建新的记录代次，不能拼接两个版本的错误。

如果数量超过默认展示上限，界面注明可展开完整列表，默认仍可紧凑显示；复制与填入始终包含该次快照中的全部诊断。致命错误后的未处理源码不凭空生成诊断，保持解析器既有语义。

点击操作时固定诊断代次、数量与对应标题，从同一版本取得正文，避免流式更新让标题数量与实际条数不一致。导出在现有串行队列中读取对应记录前缀，完成后切回 UI 更新草稿或剪贴板；旧代次已失效时取消该操作，不混用新旧内容。

### 接入输入框与保护现有内容

新增独立的诊断草稿事件，沿以下现有组件链传递：

`VisualizationBlock → AssistantMessageMarkdown → MessagePartsBlock / ChatMessage → ChatList → ChatPage → ChatInputState`

Markdown 中间层继续借助现有 fence renderer 闭包传递能力，不另建发送通道。现有 `onVisualizationMessage` 会直接进入发送路径，因此不能用来承载诊断填入。

草稿规则固定如下：

- 输入框为空：直接填入诊断全文，光标置于末尾并聚焦输入框。
- 已有普通草稿：保留原文本，在末尾追加诊断；仅在必要时插入一个换行，不增加说明性文字，不覆盖附件。
- 正在编辑历史消息：保持原编辑内容，提示先退出消息编辑；复制操作仍可用。
- 正在生成：允许填入和复制，是否可发送继续由现有发送按钮规则决定。
- 重复点击：每次都是显式编辑操作，不自动发送；操作处理中暂时禁用同一入口，避免一次点击因重入被追加两次。

事件携带来源会话、当前选中消息身份、part、fence 与诊断代次。操作完成前检查当前会话和消息分支仍匹配，来源没有被删除或替换。流式内容正常追加不使已固定的同代诊断快照失效；源码重写或切换分支则取消旧操作。全屏查看器关闭并聚焦输入框也以归属检查通过、填入成功为前提。

## 交互页面全屏、缩放和平移的完整处理

### 打开方式与全屏布局

卡片标题区新增明确的“放大查看”入口；点按非交互的图形画布也可打开。按钮、滑块、选择控件和数值输入保持原操作，不将整张交互卡片包进统一点击监听。

全屏采用与函数图相同类型的 Dialog 容器，包含标题、关闭入口和诊断菜单。页面主体继续渲染真实 Compose 内容，支持纵向滚动。图形区域具有确定的可用高度和裁剪边界；单图尽量利用剩余空间，多图按各自区块排布，不能让纵向无限约束导致画布高度异常。

手机处理状态栏、导航栏和键盘安全区域；平板利用实际窗口宽高，不额外套入手机限宽与居中布局。需要区分手机行为时，以最小窗口宽度小于 600dp 判断，不复用聊天侧栏显示条件。

系统返回键、工具栏关闭和系统允许的关闭手势都只关闭查看器，不重置可视化内容或跳转会话。

### 会话与 UI 状态的所有权

由 `ChatPage` 中位于 LazyColumn 之外的稳定宿主持有展开状态和 Dialog，按 `sessionKey` 与来源身份隔离。卡片只提交展开请求；全屏层读取同一个 `VizSession`、frame、交互 state 和诊断结果，不能再创建一份完整 `VisualizationBlock`。这样即使原卡片因列表布局变化被回收，查看器也仍有明确的宿主。

增加按来源管理的展示协调器，将当前卡片中的加载及流推进逻辑收敛为每个来源一个任务。卡片和展开宿主登记对来源的使用关系，共享结果流；展开中的来源还根据 `ChatPage` 当前会话消息中的 message identity、part 和 fence 读取最新源码，不依赖原卡片是否仍在组合树中。所有更新进入原有 Store 串行处理路径，防止两个展示位置重复提交同一批记录，也避免卡片被回收后全屏停止更新。

Store 为当前展开的 Entry 提供临时持有句柄，缓存淘汰跳过仍被查看器持有的 Entry；每个聊天页只允许一个展开对象，缓存仍按既有容量淘汰其他未持有对象。关闭查看器时释放句柄。持有只能延缓普通缓存淘汰，不能越过来源删除、分支切换、会话清理或源码版本替换；这些事件由稳定宿主先关闭查看器，再按原规则释放 session。

保留唯一的活动 renderer：展开时，卡片位置留下原尺寸占位和必要外壳，交互内容只挂载在查看器；关闭后回到卡片。协调器持续向活动展示位置提供会话结果，展开并不停止流式生成。

仅共享 `VizSession` 还不足以保存数值输入中尚未提交的文字。将这类组件局部草稿提升到按 session 和节点 identity 保存的 UI 状态容器，两个展示位置轮流读取同一份状态。切换展示位置时关闭下拉菜单等依赖原窗口锚点的临时弹层，保留未提交文本、有效交互值和页面滚动位置。

不在展开、关闭或 renderer 切换时调用 `session.reset()`、`session.close()` 或 `store.clear()`。会话销毁仍由原有 ViewModel、Entry 与分支保留机制负责。所选消息分支消失、来源删除、会话切换或 session 被替换时，关闭对应查看器并释放其局部视图状态。

打开期间，聊天滚动控制器暂停背景自动定位并保存消息锚点。普通列表回收不关闭查看器；真正的来源失效才关闭查看器并释放持有句柄。临时草稿、每个 scene 的视窗和页面位置由稳定宿主的来源状态容器保存，不寄存在可能被回收的卡片中。

### 图形视窗模型

为每个 scene 增加独立 viewport，键使用 `sessionKey + scene 的引擎 identity`。优先使用实际节点 ID，没有显式 ID 时沿用引擎的稳定路径，不能只用当前图元数量或标题识别 scene。

视窗保存世界坐标中心、短边可见的世界坐标范围以及是否经过手动调整。初始视图按真实画布尺寸完整容纳 scene：

`fitScale = min(画布宽 / scene宽, 画布高 / scene高)`

横纵统一使用同一个比例，图形居中且保持几何比例。手动视窗以中心和短边世界范围换算绘制比例；旋转屏幕、切换预览与全屏、改变窗口尺寸时，默认视图重新适配原始 scene，已调整视图保留中心和短边范围，避免反复切换后累计缩小。

提供以下操作：

- 双指捏合连续缩放，缩放中心跟随两指中心对应的世界坐标。
- 放大、缩小按钮每次改变约 1.25 倍，支持触屏以外的操作方式。
- 单指拖动放大后的画布进行平移；双指也可同时平移。
- 双击图形画布或点击“复位”恢复完整适配视图。

相对当前完整适配比例，缩放范围限制在 0.5–8 倍；比例必须有限且大于零。窗口尺寸大幅变化时只有超出边界才夹取有效范围，正常变化保持已保存视窗。平移允许少量边缘留白，但限制不能把全部图形拖出画面。

通过 Canvas 坐标变换重新绘制矢量内容，并裁剪在图形区域内；不要放大整页截图或整体缩放包含原生控件的 Column。图内文字、线条和图元统一跟随图形比例；外围按钮、滑块和输入框保持原生尺寸。

一个页面存在多个 scene 时，各自持有 viewport 和缩放控件，复位仅影响所在 scene。只有原生控件、没有 scene 的页面仍支持全屏展开和页面滚动，不显示没有作用的缩放按钮。

### 手势分配与原生交互

卡片预览保留聊天滚动体验，不在预览直接接管捏合和平移；点击画布打开查看器后再进行视图操作。

全屏的缩放和图形拖动只在 scene 区域处理：

- 完整适配或更小比例时，单指纵向拖动优先滚动交互页面。
- 放大后，单指拖动优先平移当前画布；到达允许的平移边界时，通过嵌套滚动把未消费的纵向位移交给页面。
- 双指变换由画布处理，不同时触发页面滚动。
- 滑块、数值输入、按钮和选择菜单保留各自事件，父容器不拦截它们的操作。
- 双击只在图形区域复位，不影响输入框选择文字或按钮点击。

此次不新增图元命中、拖动节点、编辑连线等能力。现有页面中触发 AI 消息的交互动作仍走原有消息发送校验，诊断填入走独立草稿事件，两种行为保持清晰。

### 流式生成、错误和退出恢复

生成期间可以打开已经具备可渲染 scene 的查看器；后续记录继续更新同一个 session。未初始化出可渲染页面时，不提供空白的放大入口，但保留已有诊断的复制和填入能力。

没有手动调整过视窗时，scene 的有效尺寸变化后重新完整适配；已经调整过时保留用户视窗，只做必要边界约束。普通图元追加不重置缩放。`INCOMPLETE`、生成取消或部分记录错误时保留可用画面，同时展示原有状态和诊断。

关闭查看器时，恢复同一消息中的卡片状态和来源位置；新的卡片高度进入布局后，由聊天滚动控制器按保存锚点恢复。若该位置已经不是底部，则转入浏览状态，避免刚关闭就被生成跟随拉走；仍在底部时可以继续跟随。整个过程不向会话历史插入消息，不重新创建对话。

缩放操作只更新视窗和绘制，不重新解析源码或重新运行整个可视化求值。打开前后都只有一份活动交互控件树，避免重复绘制、输入焦点竞争及两个局部草稿互相覆盖。
